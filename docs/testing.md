## 도메인 검사

```bash
.venv/bin/python tests/domain_checks.py
.venv/bin/python tests/repository_checks.py
```

다음을 실제 SQLite DB에서 확인한다.

- 비밀번호 해시 저장
- `User → Project → Task` 두 개의 1:N 관계
- 허용·차단되는 상태 전이
- 사용자 삭제 시 프로젝트와 할 일 cascade 삭제
- ID 재사용과 동시 요청에서 소유권·상태 전이 보호
- 커밋 후 다른 사용자 데이터가 반환되지 않는지 검사
- 프로젝트 목록의 연관 작업 조회에서 소유권 재검사
- `RETURNING`을 지원하지 않는 SQLite 모드에서 생성·조회·변경·삭제

저장소는 SQLite 3.35의 `RETURNING` 구문에 의존하지 않는다. 실제 SQLite **3.34.1**과 **3.53.1**에서 도메인 11개, 저장소 회귀 4개, HTTP 통합 5개 검사를 각각 통과했다.

## HTTP 통합 검사

서버를 실행한 상태에서 다음 명령을 사용한다.

```bash
FLOWTASK_BASE_URL=http://127.0.0.1:8000 \
  .venv/bin/python tests/integration_smoke.py
```

익명 접근 차단, 로그인 성공·실패, 회원가입, 사용자별 인가, 프로젝트·할 일 생성, 상태 변경, 검색·필터, CSRF, 로그아웃, OAuth 미설정 오류, 404를 검증한다.

현재 HTTP 통합 검사는 HTTPS 스타일 경로 검사까지 포함해 6개이다. 도메인 11개·저장소 회귀 4개와 합쳐 자동 검사 21개를 구성한다. 앞의 SQLite 버전별 20개 통과 기록은 HTTPS 스타일 검사 추가 전의 검증 결과다.

2026-11-07 main 통합 전 별도 임시 DB와 OAuth 미설정 로컬 서버에서 21개 검사를 모두 통과했다. Python 파일 28개의 구문, 문서 7개의 링크·코드 블록, Render YAML 구문 검사도 통과했다.

브라우저 QA 결과와 증거 화면은 `.gstack/qa-reports/`에 저장되며 2026-07-28 기준 점수는 **100/100**이다.

## 실행 시 유의 사항

- 명령은 저장소 루트에서 실행한다. 가상환경이 활성화돼 있다면 `.venv/bin/python` 대신 `python`을 사용할 수 있다.
- 도메인·저장소 검사는 각각 임시 SQLite DB를 사용한다.
- HTTP 통합 검사는 대상 서버에 테스트용 계정·프로젝트·할 일을 생성하고 변경하므로 별도의 테스트 서버와 DB를 사용한다.
- 전체 HTTP 통합 검사는 `GITHUB_CLIENT_ID`와 `GITHUB_CLIENT_SECRET`을 설정하지 않은 테스트 서버를 기준으로 한다. OAuth 설정 후에는 정상 동작이 503 오류에서 GitHub 인증 페이지로의 302 이동으로 바뀌므로, 설정된 공개 서버에는 미설정 상태를 가정하는 전체 검사를 그대로 적용하지 않는다.
- 다른 포트로 실행했다면 `FLOWTASK_BASE_URL`도 같은 주소로 변경한다.
- 위 SQLite 버전별 결과와 2026-07-28 QA 점수는 기존 검증 기록이다. `.gstack/`는 로컬 검사 산출물이며 Git 추적 대상에서 제외돼 있다.
- 제출용 화면 자료는 [화면 자료 문서](screenshots.md)에 정리돼 있다.

## 공개 서버 검증

2026-11-03 이전 배포 환경에서 HTTP 통합 검사 6개를 통과했다. 당시에는 GitHub OAuth 키를 설정하지 않은 상태였다. 브라우저에서도 데모 로그인, 프로젝트·할 일 생성, 대기 → 진행 중 → 완료 상태 변경을 확인했다. HTTPS 프록시 뒤에서 스타일 파일이 공개 사이트의 HTTPS 주소로 로드되는지 확인하는 회귀 검사도 포함한다.

2026-11-07 [Render 공개 서버](https://b6-3.onrender.com/)에서 다음을 확인했다.

| 검증 항목 | 결과 |
| --- | --- |
| 홈·로그인·회원가입·스타일 파일 | HTTP 200 |
| `/health` | HTTP 200, `{"status":"ok"}` |
| 비로그인 보호 화면 접근 | `/app/projects` → 로그인 화면, HTTP 303 |
| 데모 로그인·세션 유지·로그아웃 | 정상, 세션 쿠키 `Secure` 확인 |
| GitHub 인증 시작 | GitHub 인증 페이지로 HTTP 302 이동 |

검증 당시 배포 화면은 최신 수정 전 버전이었다. main 통합본을 배포한 뒤 프로젝트·할 일 생성과 상태 변경, 최신 UI 반영 여부를 다시 확인한다. GitHub 실제 계정 로그인과 새로고침 후 로그인 상태 유지는 같은 날 사용자가 직접 확인했다.

무료 서버의 재시작·재배포 시 SQLite 데이터가 초기화될 수 있으며, 데모 계정은 시작 시 다시 생성된다.

### GitHub 소셜 로그인 실계정 검증

2026-11-07 사용자가 Render 공개 주소에서 실제 GitHub 계정 로그인과 새로고침 후 로그인 상태 유지를 직접 확인했다.

아래 표와 화면 자료는 2026-11-04 이전 배포 환경에서 수행한 검증 기록이다.

| 검증 항목 | 결과 |
| --- | --- |
| 설정 반영 배포 | 배포 성공, 서비스 실행 확인 |
| GitHub 인증 시작 | `/auth/github` → GitHub 인증 페이지, HTTP 302 |
| 실제 계정 인증 완료 | `/auth/github/callback` → 프로젝트 화면, HTTP 303 |
| 로그인 성공 화면 | GitHub 로그인 성공 안내와 계정 이름 표시 |
| 보호 화면 접근 | 로그인한 계정의 `/app/projects` 진입 |
| 세션 유지 | 새로고침 후에도 같은 계정으로 프로젝트 화면 표시 |

실제 GitHub 계정 승인은 사용자가 직접 진행했다. 인증 코드·토큰·Client secret은 문서에 기록하지 않는다. 확인 화면은 [화면 자료](screenshots.md#github-소셜-로그인)에 있다.
